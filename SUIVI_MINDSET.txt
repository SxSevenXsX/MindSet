1. INTENTION ET CONTRAINTES DU PROJET
-----------------------------------
MindSet est une application personnelle de notes sous Windows. Elle conserve sa
structure propre : boîtes indépendantes, dossiers, notes, onglets, signets, vue
arbre et audio. L’inspiration Notion/Obsidian porte surtout sur la fluidité de
l’écriture, la simplicité et les commandes de blocs ; il ne s’agit pas de jeter
la construction existante pour une démonstration visuelle sans fonctions.

Demandes exprimées :
- Fiabiliser le « mini Word » : texte saisi au bon endroit, curseur stable,
  titres, retours simples, paragraphes, listes, sauts explicites et impression.
- Police plus simple, lisible et agréable ; interface propre et cohérente.
- Choix rapide de blocs/annotations avec le menu « / ».
- Parcours de mise à jour conservé : rechercher, télécharger, redémarrer.
- Priorité à une solution gratuite, sans abonnement. Aucun achat de certificat,
  aucun contrat et aucune souscription à un service n’ont été autorisés.
- Import/export des boîtes depuis l’accueil, en conservant l’audio.
- Guide complet dans la boîte de départ, en bas de l’accueil.
- Journal texte complet permettant de reprendre le projet sans réinventer son
  historique ni perdre de vue ce qui reste effectivement à faire.
- Sources sur GitHub ; ne pas publier par erreur des données privées.

2. CORRECTION IMPORTANTE DU DIAGNOSTIC UTILISATEUR
------------------------------------------------
L’utilisateur a d’abord cru que toutes ses boîtes avaient disparu. Il a ensuite
précisé qu’elles étaient toujours présentes : il avait ouvert MindSet alors
qu’une autre instance tournait déjà et avait vu une seconde fenêtre vide.
Il ne faut donc PAS présenter cet épisode comme une perte de données confirmée.
La cause exacte du contenu vide de l’ancienne seconde fenêtre n’est pas prouvée.
En revanche, le code autorisait plusieurs processus principaux concurrents.

La demande antérieure de fermer MindSet concernait uniquement une éventuelle
copie cohérente de récupération. Elle ne s’applique pas à l’utilisation normale
ni aux nouveaux boutons d’export. Les exports doivent fonctionner en laissant
MindSet ouvert. L’utilisateur peut continuer à utiliser son installation actuelle.
Aucun arrêt forcé, aucune désinstallation et aucune restauration de ses boîtes
personnelles n’ont été effectués au cours de cette intervention.

3. ARCHITECTURE À CONNAÎTRE
--------------------------
- Electron : electron/main.js, preload isolé dans electron/preload.js.
- Interface sans framework : index.html, src/app.js, src/styles.css.
- Éditeur : src/editor-document.js, src/editor-blocks.js, editor-blocks.css.
- Stockage principal : localStorage, clé « mindset.state.v1 ».
- Audio : IndexedDB « mindset-audio », magasin « clips », index « boxId ».
- Profil installé constaté lors du diagnostic : %APPDATA%/mindset.
- Installation constatée : %LOCALAPPDATA%/Programs/MindSet.
- Profil de développement désormais distinct : %APPDATA%/mindset-development.
- MINDSET_DEV_PROFILE permet un profil de test dédié uniquement en développement.
  Cette variable n’altère pas le profil de l’application empaquetée.

Une boîte non protégée contient son arborescence root (dossiers, notes, audio),
les identifiants actifs, sélections, onglets et signets. Une note conserve son
HTML. Les images intégrées vivent dans ce HTML ; une image distante reste liée
à son site d’origine. Les clips audio conservent leur fiche dans l’arborescence,
mais les octets se trouvent dans IndexedDB.

Une boîte protégée est enregistrée sous forme chiffrée. Le contenu et les octets
audio utilisent AES-GCM ; la clé est dérivée du code avec PBKDF2/SHA-256,
310 000 itérations. Le nom de la boîte reste visible. Des états audio transitoires
peuvent conserver une variante pending lors d’un changement de protection.
Les anciennes boîtes protégées en clair sont migrées à leur ouverture.

Attention : persistState() reste synchrone et renvoie un booléen ; plusieurs
parcours s’appuient sur ce contrat. flushAppState() attend les écritures audio,
termine la capture de l’éditeur et le chiffrement avant de confirmer une fermeture.
Ne pas remplacer cette logique par un simple délai arbitraire.

7. CE QUI EST AJOUTÉ EN 1.3.4
----------------------------
7.1 Une seule instance
- Verrou Electron demandé avant création de fenêtre et chargement des données.
- Second processus : sortie immédiate ; le premier affiche et met au premier
  plan sa fenêtre. Une fenêtre réduite est restaurée.
- Second lancement pendant le démarrage : focus différé jusqu’à la disponibilité
  de la fenêtre.
- Développement et installation n’utilisent plus le même profil.
- Lors du premier passage depuis l’ancienne version, fermer normalement ses
  anciennes fenêtres : une version dépourvue de verrou ne peut pas être corrigée
  rétroactivement par le nouveau processus.

7.2 Fichiers de boîtes .mindset
- Bouton Importer des boîtes à côté de Nouvelle boîte.
- Bouton Exporter sur chaque carte et Sauvegarder toutes les boîtes sur l’accueil.
- Fichier contenant boîtes et octets audio ; application laissée ouverte.
- Export après synchronisation des notes et du chiffrement ; copie cohérente
  de l’état pendant le verrouillage des modifications audio.
- Sauvegarde native dans Electron ; téléchargement habituel dans le navigateur.
- Écriture native dans un fichier temporaire puis renommage vers la destination.
- Annulation de l’enregistrement : message d’annulation, sans succès artificiel.
- Version du format : 1, identifiant « mindset-backup », empreinte SHA-256 du
  contenu pour détecter une troncature ou modification accidentelle.
  Cette empreinte n’est PAS une signature d’auteur ni une preuve d’authenticité.
- Vérification du format, des identifiants, de l’arbre, des données encodées,
  des tailles et des références audio.
- Refus d’un export incomplet si un clip d’une boîte inspectable manque.
- Chiffrement conservé ; refus d’exporter une boîte protégée contenant du clair.
- Les variantes audio transitoires sont conservées lorsqu’elles restent chiffrées.
- Limite de 256 Mo par fichier ; possibilité d’exporter les boîtes séparément.

7.3 Import sans écrasement
- Vérification puis résumé avant confirmation.
- Une boîte déjà présente, reconnue par son identifiant, est ignorée et conservée.
- L’import ne remplace PAS une boîte existante par une ancienne sauvegarde.
- Une collision d’identifiant audio provoque un refus, jamais un remplacement.
- Ajout des nouveaux clips dans une transaction utilisant add(), pas put().
- Échec de persistance de l’état : restauration de la liste antérieure et retrait
  des seuls audios ajoutés pendant cette tentative.
- Les opérations d’import/export empêchent les actions concurrentes de l’interface.
- DOMPurify 3.4.15, distribué localement avec ses licences, nettoie le HTML importé.
- Les attributs pouvant déclencher les actions de l’application et les styles
  pouvant recouvrir l’interface ne sont pas repris.
- Conservation des titres, styles personnels, listes de tâches, couleurs, images,
  tableaux, sauts explicites ; couleurs et provenance des clips audio conservées.
- Pour les boîtes chiffrées importées, la structure et le HTML sont vérifiés au
  déverrouillage, quand le contenu devient accessible. Ce contrôle est conservé
  dans le stockage grâce au marqueur archiveImported.

Limites assumées du fichier :
- Les préférences globales d’affichage, styles définis dans les paramètres et
  polices locales ne sont pas transportés. Les références de style et mises en
  forme intégrées aux notes sont conservées ; l’apparence peut donc dépendre des
  paramètres de l’ordinateur de destination. L’accueil et le guide le précisent.
- Les liens vers des images distantes ne deviennent pas des fichiers autonomes.
- Une boîte protégée nécessite toujours son code ; celui-ci n’est pas récupérable.
- Sans déverrouiller une boîte chiffrée, l’export ne peut pas vérifier que chaque
  référence interne correspond à un clip ; il emporte tous ses enregistrements.
- L’écriture de l’état et des octets audio utilise deux stockages distincts.
  Le retour arrière est testé en cas d’erreur normale ; ce n’est pas une
  transaction physique unique résistante à toutes les pannes du système.

7.4 Stockage protégé contre le faux « premier démarrage »
- Absence de données, stockage illisible et liste volontairement vide sont
  distingués.
- Erreur de lecture/JSON/arbre : écran explicite et écritures suspendues.
- Aucun nettoyage des octets audio dans cet état.
- Boutons Réessayer et, lorsque le texte brut a pu être lu, copie locale des
  données pour diagnostic. Cette copie n’est pas une archive complète .mindset.
- Le stockage d’origine reste inchangé tant que la lecture n’est pas réparée.

7.5 Guide et présentation
- Guide MindSet : cinq dossiers, seize notes explicatives.
- Bien démarrer ; écrire et mettre en forme ; vue arbre/audio ; sauvegarder et
  protéger ; application, mises à jour, raccourcis et nouveautés.
- Affiché sous les boîtes de projet, dans une zone dédiée en bas de l’accueil.
- Ajouté aux espaces existants sans supprimer leur ancienne boîte de démarrage.
- Le guide est modifiable ; son contenu n’est pas réécrit à chaque lancement.
- Bouton Guide MindSet : ouvrir le guide ou le recréer s’il a été supprimé.
- Cartes élargies pour accueillir Exporter ; statut non protégé plus discret.
- Bouton Recentrer dans la vue arbre : remise à zéro du déplacement et zoom 100 %.
- Les modules d’écriture 1.3.2 sont conservés ; pas de refonte arbitraire des
  raccourcis ou du modèle de documents pendant l’ajout des sauvegardes.

11. PUBLICATION, INSTALLATION ET PISTES GRATUITES
------------------------------------------------
La version 1.3.4 est une version de sources préparée. Une construction locale
sans installation sert à vérifier les fichiers embarqués. Elle ne prouve pas
que Windows acceptera un nouvel installeur.

Aucune version 1.3.4 publique n’est déclarée prête à télécharger ici.
Aucun nouveau tag de publication n’est créé pour contourner les contrôles.
Ne pas désinstaller la version actuelle en supposant qu’un EXE non signé sera
forcément accepté. Une mise à jour en place conserve normalement le profil ;
une suppression explicite des données lors d’une désinstallation ne le conserve
pas. Une vraie sauvegarde vérifiée doit précéder toute opération de ce type.

Pistes étudiées et limites (voir docs/windows-signing.md pour les liens) :
- SignPath Foundation : programme gratuit pour projets open source éligibles,
  admission non garantie ; aucune candidature déposée.
- Réexamen Microsoft/Smart App Control du fichier bloqué : possibilité à vérifier,
  aucun déblocage garanti pour ce fichier ou les suivants ; aucun envoi réalisé.
- Les offres payantes de certificats ont une durée de validité et des conditions ;
  elles ne constituent pas une signature illimitée acquise définitivement à petit
  prix. Aucun abonnement ni achat n’a été effectué.
- Ne pas désactiver Smart App Control ni déplacer/remplacer des composants pour
  contourner le blocage. Une signature ne dispense pas d’un test d’installation.

Priorité C — qualité continue :

- Mettre à jour le guide pour chaque fonction réellement livrée. Préserver les
